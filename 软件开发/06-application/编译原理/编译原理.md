

# 自举原理初探

编程语言的自举（Bootstrapping）是指一种编程语言能够编译自身编译器的过程。简单来说，就是：先用其他语言（或该语言的早期版本）编写一个基础编译器，再用该语言本身编写更完善的编译器源码，最后用基础编译器编译这个源码，得到可编译自身的 “自举编译器”。

**自举的核心步骤**，这里以C语言和mini语言为例: **阶段1**：用C语言编写mini语言的基础编译器（能编译mini语言的核心语法） **阶段2**：用语言 B 编写语言 B 的完整编译器源码（功能与阶段 1 的编译器等效，甚至更强）


mini_print.c 编译源代码如下：
```cpp
#include <stdio.h>
#include <string.h>
#include <stdlib.h>

// 核心功能：将MiniLang代码转换为C代码
void mini_to_c(const char* input_file, const char* output_c) {
    FILE *in = fopen(input_file, "r");
    FILE *out = fopen(output_c, "w");
    if (!in || !out) { perror("文件打开失败"); exit(1); }

    // 生成C代码的头部
    fprintf(out, "#include <stdio.h>\n");
    fprintf(out, "int main() {\n");

    char line[1024];
    while (fgets(line, sizeof(line), in)) {
        // 解析MiniLang的print语句：提取双引号 "" 中的内容
        char* print_keyword = strstr(line, "print ");
        if (print_keyword) {
            char* start = strchr(line, '"');
            char* end = start ? strrchr(line, '"') : NULL;
            if (start && end && start < end) {
                // 提取字符串内容，生成printf语句
                *end = '\0'; // 截断末尾的"
                fprintf(out, "    printf(\"%s\\n\");\n", start + 1);
            }
        }
    }

    // 生成C代码的尾部
    fprintf(out, "    return 0;\n");
    fprintf(out, "}\n");

    fclose(in);
    fclose(out);
}

int main(int argc, char* argv[]) {
    if (argc != 3) {
        printf("用法：%s <input.mini> <output.c>\n", argv[0]);
        return 1;
    }
    const char *input_mini = argv[1];
    const char *output_c = argv[2];

    // 1. 将MiniLang代码转换为C代码
    mini_to_c(input_mini, output_c);

    printf("转换完成：生成C代码文件 %s\n", output_c);
    return 0;
}
```

# 移动语义

**提问豆包**: 用C语言写一个最小编译器，用来实现移动语义

**豆包回答**: 要实现一个支持 “移动语义” 的最小编译器，我们需要设计一个极简的编程语言（包含移动操作语法），并通过编译器将其转换为 C 代码（利用之前模拟移动语义的方式）。


**整体设计**:

- 定义语法；
- 编译器功能：
    - 词法分析：将源代码解析为 token（关键字、标识符、符号等）
    - 语法分析：构建抽象语法树（AST），识别移动操作
    - 代码生成：将 AST 转换为 C 代码，用`buffer_move`函数实现移动语义


**步骤1：定义mini语法**

支持以下语法:
```
// 声明Buffer变量（大小为数字）
Buffer 变量名(大小);

// 普通赋值（深拷贝）
变量名 = 变量名;

// 移动操作（资源转移）
变量名 = move(变量名);

// 写入数据
变量名.write("字符串");

// 打印变量状态
print(变量名);
```



示例程序（test.mini）：
```
Buffer a(100);    // 声明a，大小100
a.write("aaaaa"); // 写入数据
print(a);         // 打印a

Buffer b(50);     // 声明b
b = move(a);      // 移动a到b（a失去资源）
print(a);         // 打印a（应显示无资源）
print(b);         // 打印b（应显示a的数据）

Buffer c(10);
c = b;            // 普通赋值（深拷贝）：c = b;
print(c);         // 打印c（应显示a的数据）
print(b);         // 打印b（应显示a的数据）
```


下面是用于测试的无注释版代码(因为当前实现的编译器不支持注释语句的解析)：
```
Buffer a(100);
a.write("aaaaa");
print(a);

Buffer b(50);
b = move(a);
print(a);
print(b);

Buffer c(10);
c = b;
print(c);
print(b);
```

**步骤3：使用编译器**
下面是编译器使用流程：

```bash
#先把编译器编译出来
gcc mini_move.c -o mini_move.elf

#然后用编译器去编译测试代码
./mini_move.elf test_move.mini test_move.c

#把最终代码再次编译成可执行程序
gcc test_move.c && ./a.out
```


**核心原理说明：**

1. **移动语义的实现**：编译器将源语言的`b = move(a)`转换为 C 代码的`buffer_move(&b, &a)`，实现资源所有权转移（`a`的`data`指针被置空，`b`接管内存）。
2. **与普通赋值的区别**：普通赋值（`b = a`）被转换为深拷贝（重新分配内存并复制内容），而移动操作仅转移指针，避免内存拷贝，体现 “移动语义” 的高效性。
3. **编译器流程**：
    - 词法分析：将源代码拆分为`Token`（如`Buffer`、`move`、标识符等）。
    - 语法分析：根据 Token 构建 AST，区分声明、赋值、移动等操作。
    - 代码生成：将 AST 转换为带`buffer_move`等函数的 C 代码，完成移动语义的模拟。

这个最小编译器展示了移动语义的核心思想（资源所有权转移），以及如何通过编译过程将高级语法转换为底层实现。实际编译器会更复杂，但核心原理一致。

Rust语言的赋值语句默认就是移动语义，如果开发者想深拷贝，就要明确使用clone这个trait。



# Rust编程语言

- 所有的程序都必须和计算机内存打交道，如何从内存中申请空间来存放程序的运行内容，如何在不需要的时候释放这些空间，成了重中之重，也是所有编程语言设计的难点之一。在计算机语言不断演变过程中，出现了三种流派：
    - **垃圾回收**：在程序运行时不断寻找不再使用的内存，典型代表：Java、Go。
    - **手动管理内存**：在程序中，通过函数调用的方式来申请和释放内存，典型代表：C/C++。
    - **通过所有权来管理内存**：编译器在编译时会根据一系列规则进行检查。

其中 Rust 选择了第三种，最妙的是，这种****检查只发生在编译期****，因此对于程序运行期，不会有任何性能上的损失。由于所有权是一个新概念，因此读者需要花费一些时间来掌握它，一旦掌握，海阔天空任你飞跃。

## 所有权（Ownership）


新增关键字 `own` 标记**独占所有权指针 / 堆内存**，规则：
1. 一块堆内存**同一时刻仅有一个所有者**；
2. 所有者作用域结束时，**自动插入 C 的 free**（编译期处理，无运行时）；
3. 禁止所有者重复释放、野指针。

```cpp
// CRI 所有权用法（C风格）
void test(void)
{
    // own：独占所有权，编译期标记为堆内存所有者
    own int* ptr = cri_malloc(sizeof(int)); 
    *ptr = 100;

    // 编译报错：所有权不可直接拷贝（禁止双重释放）
    // own int* ptr2 = ptr; 

    // 转移所有权：move 语法（极简）
    own int* ptr2 = move ptr; 

    // 作用域结束：编译器自动在转译C代码末尾插入 free(ptr2);
}
```

**转译后的标准 C 代码**（零开销）：
```cpp
void test(void)
{
    int* ptr = malloc(sizeof(int));
    *ptr = 100;
    int* ptr2 = ptr;
    ptr = NULL; // 编译器自动置空，杜绝野指针
    free(ptr2); // 编译期插入释放逻辑
}
```



## 借用（Borrow）


新增 `borrow` 标记**只读 / 可变借用**，对标 Rust 借用规则，语法贴合 C 指针：
- 只读借用：允许多个同时存在，禁止可变借用；
- 可变借用：同一时刻仅允许一个，禁止只读借用；
- 借用生命周期不能超过所有者生命周期。

```cpp
// 只读借用 &borrow
void read_data(borrow const int* p)
{
    cri_print("%d\n", *p);
}

// 可变借用 &mut borrow
void write_data(borrow int* p)
{
    *p += 10;
}

void demo(void)
{
    own int* data = cri_malloc(sizeof(int));
    *data = 50;

    borrow const int* r1 = data;
    borrow const int* r2 = data; // 合法：多个只读借用
    read_data(r1);
    read_data(r2);

    // 编译报错：存在只读借用时，禁止可变借用
    // borrow int* w1 = data;

    // 只读借用失效后，可变借用合法
    write_data(data);
}
```



## 生命周期（Lifetime）


针对复杂跨函数借用场景，**简化 Rust 生命周期语法**，采用**隐式生命周期 + 少量显式标注**（C 开发者易理解）：

1. 简单场景：**隐式推导生命周期**（编译器自动分析，无需手写）；
2. 复杂场景：用简短字符 `'a`/`'b` 标注，仅约束指针存活范围，语法极简。


```cpp

// 显式生命周期标注（仅复杂场景使用）
int* 'a get_ptr(borrow int* 'a src)
{
    return src;
}
```

规则：保证返回的指针生命周期不超过入参，编译期杜绝**悬垂指针**。
> 核心优势：90% 业务代码无需手动写生命周期，仅底层库代码需要标注，大幅降低学习成本。



## 错误处理

错误处理（Zig 风格：显式向上传递，极简语法）

对标 Zig 的错误传播机制，**不引入异常**，基于 C 返回值做语法增强，错误链路清晰、层层向上传递。

1. 新增 `error` 关键字定义错误码集合；
2. 函数可标记 `!` 表示**可能返回错误**；
3. `try` 语法：自动向上传播错误（核心语法糖，零成本）；
4. `catch` 语法：本地捕获并处理错误。


```cpp
// 1. 定义错误集合（全局/模块内）
error FileErr {
    NotFound,
    PermissionDenied,
    IOError
};

// 2. 函数标记 !FileErr：可能返回FileErr类型错误
File!FileErr file_open(const char* path);

void main(void) !FileErr
{
    // try：遇到错误直接向上抛出，等价于传统C的if判断
    File f = try file_open("test.txt");

    // catch：本地捕获错误，降级处理
    File f2 = file_open("a.txt") catch {
        cri_print("open failed\n");
        return;
    };
}
```


**转译后的标准 C 代码**（零抽象开销）：

```cpp
// 转译后纯C：用枚举表示错误，if判断传递错误
typedef enum {
    FileErr_NotFound,
    FileErr_PermissionDenied,
    FileErr_IOError,
    FileErr_Ok
} FileErr;

typedef struct {
    File handle;
    FileErr err;
} FileRet;

FileRet file_open(const char* path);

int main(void)
{
    FileRet f_ret = file_open("test.txt");
    if (f_ret.err != FileErr_Ok) {
        return f_ret.err; // 错误向上传递
    }
    File f = f_ret.handle;

    FileRet f2_ret = file_open("a.txt");
    if (f2_ret.err != FileErr_Ok) {
        printf("open failed\n");
        return 0;
    }
    File f2 = f2_ret.handle;
    return 0;
}
```

完全等价手写 C 逻辑，**零运行时开销**，同时拥有 Zig 清晰的错误链路。





## 零成本抽象（泛型、内联、模块）


所有抽象能力编译期展开，转译为普通 C 代码，无运行时开销：

1. **泛型**：C 风格模板，编译期单例化，生成对应类型的 C 函数；
2. **inline 增强**：强制内联，等价 C `inline`；
3. **模块**：替代 C 头文件，隔离命名空间，避免宏 / 全局变量冲突。

```cpp
// CRI 泛型（零成本抽象）
template <typename T>
void swap(T* a, T* b)
{
    T temp = *a;
    *a = *b;
}

void use_swap(void)
{
    int x = 1, y = 2;
    swap<int>(&x, &y); // 编译期生成 int 版本 swap

    float f1 = 1.1f, f2 = 2.2f;
    swap<float>(&f1, &f2); // 编译期生成 float 版本 swap
}
```

转译后直接生成两个独立的 C 函数，和手动编写无区别。

## 编译期检查体系（核心安全能力）


所有内存安全规则**在 CRI→C 转译阶段完成静态检查**，转译后的 C 代码仅保留业务逻辑，无任何安全校验代码，保证零成本：

1. **所有权检查**：禁止重复 move、重复释放、所有者悬空；
2. **借用规则检查**：读写借用互斥、借用不超出所有者生命周期；
3. **生命周期校验**：杜绝跨作用域悬垂指针、野指针；
4. **数组越界检查**：编译期静态数组下标校验；
5. **错误链路检查**：标记的错误必须被 `try/catch` 处理或向上传递，杜绝未处理错误。

> 补充：动态数组 / 运行时长度数组，可选择**编译期告警 + C 运行时断言**（可选关闭，适配极致性能场景）。




## 转译规则约束（保证 C 兼容性 & 零开销）

- **语法等价**：CRI 基础语句、表达式、控制流 1:1 转为 C 代码；
- **关键字降级**：`own/borrow/error/try` 等扩展关键字，编译后转为 C 枚举、结构体、普通逻辑，C 编译器无识别压力；
- **内存管理降级**：所有权自动释放 → 编译期插入 `free`；所有权转移 → 指针置空；
- **ABI 对齐**：结构体对齐、函数调用约定、数据类型完全遵循本地 C ABI；
- **无运行时库依赖**：转译产物仅依赖标准 C 库，可跑裸机、无 OS 环境。



## 源码映射与调试定位


核心目标：**调试时直接定位 `.cri` 原始源码行号，而非转译后的 `.c` 代码**，适配嵌入式 / 桌面全场景，兼容主流调试器（GDB、OpenOCD+GDB、Keil MDK、VS Code+GDB、J-Link），不破坏原有编译链路、零运行时开销。

关键依据：主流 C 编译器（GCC、Clang、ARMCC、Keil 编译器）支持 **`#line` 预处理指令**，这是实现跨源码定位的标准工业方案，嵌入式领域广泛使用。


```cpp
#line 1 "demo.cri"
#include <stdlib.h>

#line 3 "demo.cri"
int main(void)
{
#line 5 "demo.cri"
    int* ptr = malloc(sizeof(int));
#line 6 "demo.cri"
    *ptr = 123;
#line 7 "demo.cri"
    free(ptr);
    return 0;
}
```

若第 6 行 `*ptr = 123` 出现语法 / 类型错误，GCC/ARMCC 输出：
demo.cri:6: error: invalid type argument of unary ‘*’
直接指向 **原始 .cri 文件 + 行号**，而非中间 .c 文件。


---


**工程化优化规则**

1. **批量合并连续行**
    
    连续多行 CRI 代码转译后生成连续 C 代码时，不必逐行插 `#line`，仅在**源码行变更时插入**，减少冗余代码。
2. **忽略空白 / 注释行**
    
    CRI 空行、单行 / 多行注释，转译时不额外插入 `#line`，精简产物。
3. **多文件联动**
    
    多个 `.cri` 文件相互引用时，`#line` 自动切换对应文件名，跨文件调试正常。
4. **发布版本裁剪**
    
    生产 / 量产固件（关闭调试）：编译器可配置**不生成 #line 指令**，减小固件体积、无性能损耗。


---

核心方案 2：**独立位置映射文件**（离线追溯、日志定位）

针对两类特殊场景：

- 固件运行时**自定义日志、崩溃栈打印**（非调试器接管）；
- 脱离调试环境，仅通过日志 / 地址离线分析问题；

设计独立 **`.cri-loc` 位置映射文件**，纯文本格式，简单易解析。

每行格式：`C文件行号:原始CRI文件:CRI行号`

```cpp
1:demo.cri:1
3:demo.cri:3
5:demo.cri:5
6:demo.cri:6
7:demo.cri:7
```

**运行时地址→源码解析**

嵌入式代码常通过 `PC 指针(程序计数器)` 定位崩溃位置：

- 先用 C 编译器生成的 `.elf`/`.map` 文件，把 PC 地址转为 **转译后 C 文件的行号**；
- 再通过 `.cri-loc` 映射表，查表得到原始 `.cri` 文件和行号。


**命令行查询工具**

配套开发小工具 `cri-lookup`，用法：

```bash
# 根据 C 文件 + 行号，查询原始 CRI 位置
cri-lookup demo.c:5
# 输出：Source: demo.cri, Line: 5
```

适配嵌入式工程师离线排错、量产问题复盘。


**日志埋点（可选）**

CRI 可内置宏，编译期自动注入当前源码位置：
```cpp
// CRI 内置宏 __CRI_FILE__ __CRI_LINE__（编译期替换为原始源码信息）
cri_log("err happen: %s:%d", __CRI_FILE__, __CRI_LINE__);
```

转译为 C 代码后，宏直接展开为字符串常量，**零运行时开销**，日志直接输出 CRI 源码路径 + 行号。

---

<font color=blue>spawn(...) 自动形成线程边界，这个原理是什么？
</font>

spawn(worker, arg);
本身并不会神奇地防止数据竞争。
真正的作用是spawn 是编译器能够明确识别的"线程边界"
只有知道了哪里产生了新线程，编译器才能开始做跨线程分析。

先看普通C，对于 GCC 来说，pthread_create() 只是一个普通函数，
编译器并不知道这里创建了新线程，等同于程序员需要手动告知编译器这里产生了新线程。

```cpp
safe fn test()
{
    owner Buffer *buf := alloc();

    spawn worker(move(buf));

    wait_all();
}
```

比如上述代码，此时编译器看到：
```txt
Thread#0
    owns buf

spawn

Thread#1
    owns buf
```

于是得到：ownership transfer，合法。


未来CRI最好不要依赖具体RTOS，比如 spawn worker(arg);
- 在Linux生成：pthread_create(...);
- 在RT-Thread生成：rt_thread_create(...);
- 在FreeRTOS生成：xTaskCreate(...);
但是对于CRI编译器来说：spawn语义永远一致：产生新的执行流。


borrow checker真正依赖的东西
实际上 borrow checker 根本不关心：pthread、RT-Thread、FreeRTOS、Zephyr
它只关心：Execution Context  例如：Main Thread、Worker Thread、ISR
比如未来你甚至可以有：
```cpp
spawn worker();
interrupt uart_irq();
```

编译器构建：
```txt
Context#0  
Main  
  
Context#1  
Worker  
  
Context#2  
ISR
```

然后检查：某个owner 是否同时被多个Context写

# 知识描述载体


Git保存的各种commit，看起来是时间序列，实际上不是。
因为 Commit Message 无法精确表达：设计空间、决策过程、放弃的方案、性能权衡等。
例如：Fix race condition
你看到这个 commit，根本不知道：
Race 是怎么发现的
为什么不用方案A
为什么采用方案B
代价是什么
假设你看到一个人某天的状态，你无法从当前状态推导他小时候经历过什么。


人脑为什么难以理解大型系统？
因为人脑更擅长理解因果链，例如A导致B、B导致C、C导致D；
而今天的软件工程提供给你的却是最终D，
然后让你自己推导 A B C。
所以阅读大型项目时经常出现，我知道代码怎么运行，但不知道为什么这么设计。



软件最大的知识载体不是代码，不是文档，而是“决策历史（Decision History）”。
而大型软件（Linux、Windows、LLVM、Rust）真正重要的知识，恰恰存在于时间维度上的演化过程里。
这也是为什么一个资深内核工程师读源码速度很快——他脑子里往往不仅有“代码结构图”，还有一张隐含的“演化历史图”。他看到一个函数时，不只是知道它是什么，还知道它为什么会变成今天这样。


目前最接近时间维度演化的记录手段是视频，但是视频也有缺点，演化过程往往伴随着多分支试错，但视频只能跟着时间轴线性记录，并且很冗长，但是又不能倍速（比如8倍速），因为倍速过快，人脑接受不过来甚至反应不过来。
视频虽然记录了时间，但仍然不是“演化”的理想载体。
于是一个巨大问题出现：视频记录的是你走过的路，而不是问题空间。
为什么8倍速看视频没用？因为人脑理解不是靠时间长度，而是靠决策点数量。
例如：10分钟视频，只有一个核心决策，很容易理解。
例如：1分钟视频，连续20个设计决策，就很难理解。
所以本质问题不在于视频太长，而在于决策密度太高。
比如你看 pick_next_task() 只有几百行代码，但真正理解它可能需要200个历史决策，
代码本身只保存了最终决策，没有保存被否决的199个决策。
我觉得未来的知识载体应该是“可回溯决策图”

为什么当年没选ARC？  
为什么没选GC？  
为什么owner必须显式move？
这些知识根本不在代码里，也不在视频里，它存在于设计空间探索过程里。
更准确地说：
我们今天还没有一种真正适合表达“复杂系统演化历史”的知识表示方式。
文本太线性，视频太线性，代码是快照，Git是状态差异。
而复杂系统的演化本质上更像一棵不断生长、不断剪枝的决策树。


Why 只是 Decision 的属性。
所以我觉得未来的知识表示单位不是 Why，而是Decision Node  （决策节点），
我甚至觉得软件工程真正缺失的不是 Source code，而是 Decision Code。
代码告诉你系统是什么，决策图告诉你系统为什么是这样。

```txt
Decision

Question:
    如何实现内存安全？

Options:
    GC(垃圾回收)  不适合实时系统
    RC(引用计数)  运行期开销
    Ownership 零成本抽象、适合嵌入式、编译期检查

Chosen:
    Ownership 

Reasons:
    零成本
    实时性

Tradeoff:
    学习成本提高

Timestamp:
    2026-06-12

DependsOn:
    实时系统要求
```


这样多个决策节点连接起来：
```txt
D1
 ├─ D2
 │   ├─ D4
 │   └─ D5
 │
 └─ D3
     └─ D6
```

</font>

最后整个项目形成的不是代码树，而是一个**可导航、可搜索、可追溯的决策图谱（Decision Graph）**。

任何复杂系统：硬件、软件、组织、公司、科研项目，最终都能拆成：
- 为什么这样做 —— Decision Node
- 怎么做 —— Flow Node
- 做到哪一步了 —— State Node


比如对Linux内核架构从全局视角到子系统再到代码细节的熟练掌握，以及它们之间各种因果链的数量掌握这种人，基本上是架构师成长经历一样。
是的，而且你这里实际上触碰到了一个很多人误解的地方。
很多人以为架构师掌握的是：模块A、模块B、模块C这种静态知识。
但真正顶级架构师掌握的往往是：
- 为什么有模块A
- 为什么没有模块D
- 为什么A依赖B
- 为什么不能反过来
- 为什么这个接口长这样
- 为什么这个锁必须在这里
- 为什么当年这个设计失败了
也就是：决策链 + 因果链 + 演化链

很多普通工程师看到 spin_lock();，知道这是自旋锁，但不知道：
- 为什么这里必须是spinlock
- 为什么不能mutex
- 为什么不能RCU
- 为什么不能lockless
- 换掉以后影响哪些子系统
而这些为什么才是真正的架构知识。


架构师学习：寻找 Decision
```txt
当时面临什么问题？  
  
有哪些候选方案？  
  
为什么选了A而不是B？  
  
代价是什么？  
  
这个决定影响了哪些后续设计？
```


当你看到一个新知识点时，可以固定问这五个问题：
```txt
1. 它解决什么问题？

2. 为什么需要解决这个问题？

3. 有哪些替代方案？

4. 为什么最终采用这个方案？

5. 这个选择带来了什么代价？
```
